# 실제 Supabase 과목·일반인 대상 검증

검증일: 2026-11-09 (Asia/Seoul). 업무 코드 기준 `54383b9`.

**결과: 실제 DB 마이그레이션과 서버 서비스의 개설·공개·검색 검증 통과.** 실제 로그인 브라우저/API의 새 원장 계정 검증과는 구분한다. [비밀 값 없는 결과 JSON](supabase-catalog-verification.json)을 함께 보관한다.

## 마이그레이션

실제 프로젝트는 `0001_identity_catalog`만 적용된 상태였다. 기존 체크섬이 로컬 SQL과 같고 실패한 migration이 없음을 확인했다. 기존 수업·학원·수강·결제 데이터는 0건, 앱 계정은 1건, RateLimit은 2건이었다.

적용 전에 `public` 앱 데이터·제약과 기존 SQL을 Git 제외 경로 `.tmp/supabase-catalog/`에 로컬 스냅샷으로 보관했다. 계정 정보가 들어 있는 `before-data.private.json`은 공유/커밋하지 않는다. 이 스냅샷은 public 앱 범위의 논리적 사본이며 Supabase Auth·객체 파일·관리형 PITR·백업 복구 훈련을 대신하지 않는다.

`npm run db:migrate`가 아래 순서대로 성공했다. 이력 우회를 위해 0004만 수동 적용하거나 앞선 migration을 적용된 것으로 표시하지 않았다.

| ---------------------- | ------------------------- |
| 0001_identity_catalog  | 기존 적용 유지            |

네 migration의 완료 상태·SQL SHA-256 체크섬 일치를 조회했다. `0004`의 일반인 분류 13과 네 새 과목을 실제 Course와 StudentProfile에 저장해 확인했다. 데이터 삭제·reset·이력 조작은 하지 않았다.

## 개설·검색 검증 방법

기존 로그인으로 동기화된 활성 계정을 사용했다. 이 계정에는 원장 소속이나 플랫폼 관리자 권한이 없으므로 권한을 영구 부여하지 않았다. 승인 상태 합성 학원과 임시 owner membership을 **커밋되지 않는 검증 트랜잭션 안에서만** 구성했다. 실제 입점 승인이나 로그인 성공으로 보고하지 않는다.

`createOffering` → `publishOffering` → `searchOfferings`의 실제 서버 권한·검증·SQL을 같은 실제 Supabase 트랜잭션에서 실행했다. 서비스 내부 transaction callback은 외부 검증 transaction을 공유하도록 연결했다. 실행한 SQL과 제약은 실제 DB를 사용하며 테스트 DB·가짜 로그인·Supabase 토큰 주입은 사용하지 않았다.

| 분야          | 대상   | 개설 | 공개 | 해당 과목·일반인 검색 | 고3 검색에서 제외 |
| ------------- | ------ | ---- | ---- | --------------------- | ----------------- |
| 프로그래밍    | 일반인 | 통과 | 통과 | 통과                  | 통과              |
| AI 활용       | 일반인 | 통과 | 통과 | 통과                  | 통과              |
| AI 자격증     | 일반인 | 통과 | 통과 | 통과                  | 통과              |
| AI Agent 개발 | 일반인 | 통과 | 통과 | 통과                  | 통과              |

동일한 활성 계정도 소속 없는 다른 합성 학원의 수업 개설은 `FORBIDDEN`으로 거부됐다. 일반인 학습자 분류도 실제 DB에 저장할 수 있었다.

모든 합성 학원·소속·수업·회차·감사 기록·학습자는 마지막에 명시적으로 ROLLBACK했다. 다른 연결이나 공개 웹사이트에는 이 미커밋 수업이 보이지 않는다. 검증 후 실제 학원/수업/학습자/거래/감사 데이터는 다시 0건이다. 이번 검증으로 사용자에게 새 원장 권한이나 관리자 권한이 생기지는 않는다. 실제 운영 수업 등록에는 정상 입점·승인·소속 절차가 필요하다.

## 보존·접근 검사

- 마이그레이션 전후 기존 public 앱 행의 수와 JSON SHA-256을 비교해 기존 레코드 보존을 확인했다. migration 이력은 정상적으로 1개에서 4개로 증가했다.
- 검증 transaction 전후에도 전체 public 테이블 행의 SHA-256이 동일했다. 기존 계정 권한도 바뀌지 않았다.
- public 테이블 35개 모두 RLS가 활성 상태다. 별도 허용 정책이나 공개 읽기 권한을 추가하지 않았다.
- 읽기 전용 SQL에서 `SET LOCAL ROLE anon`과 `authenticated` 각각의 User 조회 결과는 0행이었다. 서버 DB 연결은 기존 BYPASSRLS 연결이므로 애플리케이션의 권한 검사는 여전히 필수다.
- 앱에서 Session pooler까지의 TLS 소켓은 암호화됐고 인증서 검증이 성공했다. `pg_stat_ssl`의 pooler→DB backend 값은 false였다. 이를 앱 앞단 TLS 실패나 전체 내부 네트워크 암호화 검증 성공으로 혼동하지 않는다.

## 재현과 한계

현재 로컬 사전 스냅샷이 있는 워크스페이스에서 다음 진단을 재실행할 수 있다. 이메일은 기존 활성 계정으로 지정하고 비밀키·토큰은 인자로 넣지 않는다.

```powershell
npx tsx --conditions=react-server scripts/verify-supabase-catalog.mts --allow-rollback-fixtures --actor-email=EXISTING_EMAIL
```

스크립트는 `.env.local`의 실제 프로젝트 일치·인증서 검증 TLS를 확인하고, 모든 검증 쓰기를 한 transaction에서 롤백한다. 과거 사전 스냅샷 이후 실제 데이터가 바뀐 경우 보존 비교는 실패할 수 있으므로 진단의 기준 스냅샷을 임의로 덮어쓰지 않는다. 계정·연결 문자열·토큰·private 스냅샷을 결과 JSON에 출력하지 않는다.

후속 `db:migrate` 재실행은 `No pending migrations to apply`로 종료했다. 진단 스크립트를 포함한 타입 검사·전체 린트도 통과했다. 신규 DB 스키마가 실제로 존재하는 것과 실결제·Daily·Storage·파일 검사기·운영 출시는 별개다. 해당 제공자를 호출하거나 환경변수·기능 플래그를 바꾸지 않았다. 기존 출시 NO-GO 조건과 백업 복구·정책·스테이징 수용 조건은 유지한다.
