# P4 장애·복구 운영 절차

이 문서는 실행 가능한 대응 순서다. 외부 경보 전달·운영 스케줄러·실제 복구 훈련은 아직 연결/완료되지 않았다. 담당자·연락 채널·응답 목표 시간은 출시 전에 지정한다.

## 관측

- 공개 `/api/health`: 생존 확인만 한다. 정상이어도 DB/결제/화상 성공을 보장하지 않는다.
- 관리자 `/api/internal/readiness`: DB SELECT1·실패 Job 개수·구성 관문. 비밀 값은 응답하지 않는다.
- `/admin/payments`: 실패/재시도 작업의 통제된 오류 코드·상태 확인. 학습 작업도 동일 claim fence·감사 원칙을 사용한다.
- 출시 전 알림: failed Job>0, 연속 readiness 실패, join/provider 5xx 증가, 파일 검사 지연·quarantine 증가, DB 연결/용량을 경보에 연결하고 실제 수신 시험한다. 수치 임계값·당직자는 운영자가 확정한다.

## 화상·학습 장애

1. 개인정보/입장 링크를 복사하지 않고 시각·수업 ID·오류 코드·요청 ID를 기록한다.
2. Daily 상태·설정·입장 시간창·현재 담당/수강권을 확인한다. 장애가 있어도 권한 검사를 우회하는 공개 방을 만들지 않는다.
3. 수업 입장 UI의 재시도를 사용한다. 실패 시 학원 담당자가 승인한 연락 채널로 대체 일정/수업을 안내한다. 자동 연락 발송은 구현하지 않았다.
4. 접속 실패를 출석으로 바꾸지 않는다. 강사가 실제 참여 확인 후 사유와 함께 정정하며 이력을 보존한다.
5. 파일 검사 실패는 quarantine을 유지한다. 재시도는 같은 제출/객체 참조를 확인하며 다른 학생 파일을 재사용하지 않는다.

## 결제·작업 복구

[payment-recovery.md](payment-recovery.md)의 서명 요청·nonce·lease·claim token·관리자 재처리 규칙을 따른다. scheduler는 매분 새 nonce와 HMAC으로 `/api/internal/jobs`를 호출해야 한다. 서명 원문에 query URL 비밀을 넣지 않는다. learning-only 구성에서는 화상/결제 공급자 호출 없이 종료 수업의 수료 작업을 실행할 수 있다. PG 미설정일 때 기존 PG 작업을 성공으로 처리하지 않는다.

중복 호출은 수강권/수료·이벤트 고유 키로 멱등하게 처리한다. 불명확한 결제/환불에 새 requestKey를 발급하지 않는다. 토큰/queue 행 직접 편집으로 claim을 강제 해제하지 않는다. 완료 작업 실패는 원인을 수정한 뒤 플랫폼 관리자 재시도로 복구한다.

## DB·배포·키

DB 장애 시 read-only 진단 후 변경을 멈추고 연결 풀·TLS·최근 migration을 확인한다. 스테이징 백업과 복구 검증 없이 운영 스키마를 수정하지 않는다. migration rollback은 자동 down SQL이 없으므로 우선 기능 플래그 `LEARNING_ENABLED=false`, 앱 이전 버전 복귀, 데이터 보존 상태에서 전진 수정한다. 파괴적 복구는 대상·백업·유실 범위를 확정한 별도 지시가 필요하다.

키 노출 시 사용 중지/제공자 폐기 → 새 키를 비밀 저장소에 설정 → 앱 재시작 → 최소 기능 확인 → 이전 키 거부 확인 → 로그/접근 범위 검토한다. Supabase·Daily·메일·PG·JOBS_SECRET은 개별로 교체한다. 채팅/저장소/스크린샷에 값을 넣지 않는다. 기존 Daily 입장 링크의 즉시 폐기는 별도 API/회의실 조치가 필요할 수 있다.

장애 종료 시 시작/탐지/복구 시각, 영향 범위, 데이터 정합성, 수동 조치, 미해결 위험과 재발 방지를 기록한다. preview 합성 검증을 실제 복구 훈련 결과로 보고하지 않는다.
